# 黄金集：迭代 ClaimAudit 用的固定基准

迭代工具最大的敌人是「改完感觉变好了」。所以这里固定一批**人工判过级的样本**，
每次改动都跑一遍，只有这张表全绿、且真实对象分数不掉，才算进步。

```bash
python bench/run.py
```

输出：

```
样本            等级   分数    期望      结果
good_lib         A     82.1    S/A       PASS
dump_repo        B     76.8    B         PASS
...
```

每个 fixture 自带期望（`_expect`）：

```json
"_expect": {"grades": ["S", "A"], "note": "成熟库：有测试、有 CI、有维护"}
```

判定规则：

* `grades` —— 等级必须落在集合里；
* 可选 `min_score` / `max_score` —— 分数的硬边界（用于抓「等级对了但分数虚高」）。

## 为什么是这七个

| 样本 | 代表什么 | 它考的是 |
|---|---|---|
| `good_lib` | 成熟开源库 | 不给真东西扣分 |
| `dump_repo` | 文档漂亮、发布即停 | **封顶规则**（commits ≤5 且建库 >30 天） |
| `abandoned` | 两年没更新、无测试 | 掉分是否够狠 |
| `no_license_claim` | 说开源但没 LICENSE | **封顶规则**独立生效 |
| `article_good` | 有出处、有数字的报道 | 内容类不该被一剑封喉 |
| `article_hype` | 私域引流、收益承诺 | 内容类该被按住 |
| `video_no_transcript` | 只有视频链接 | **拒答**（未定级） |

样本都是合成的，但事实结构取自真实见过的项目——目的是校准**规则之间的相对关系**，
不是给某个具体仓库打分。

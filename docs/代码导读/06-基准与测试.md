# 06 · 基准与测试：bench/ 与 tests/

**这一章解决一个问题：改完之后，我凭什么说它变好了？**

---

# 一、`bench/` — 黄金集

## 为什么需要它

规则系统有个恶性循环：你觉得某个案例判错了 → 改阈值 → 另外三类的分变了 → 你看不出来 → 下线。
破法只有一个：**固定一批人工判过级的样本，每次改完都跑一遍。**

## 1. `bench/golden/*.json` — 七个样本

每个文件就是一个 `payload`（和适配器返回的结构完全一样），外加一个 `_expect`：

```json
{
  "_expect": {"grades": ["S","A"], "note": "成熟库：测试、CI、文档、维护都在"},
  "source": "github",
  "facts": { ... }
}
```

| 样本 | 期望 | 它考什么 | 背后对应什么真实场景 |
|---|---|---|---|
| `good_lib` | S/A | 真东西不能被扣分 | Django/requests 这类成熟库 |
| `dump_repo` | B | **封顶**：commits ≤5 且建库 >30 天 | 文档精美、发布即停的项目 |
| `abandoned` | C/D | 两年停更 + 无测试 + 无 LICENSE + 喊“最强” | 死掉的老项目 |
| `no_license_claim` | C | 工程再好，假开源也必须封顶 | “开源但没 LICENSE” |
| `article_good` | A/B | 内容类不该被一剑封喉 | 有出处、给样本量的报道 |
| `article_hype` | C/D | 收益承诺 + 私域引流 + 零出处 | 卖课文案 |
| `video_no_transcript` | — | **拒答** | 只有抖音分享链接 |

`_expect` 支持三个字段：

- `grades`：允许的等级集合；
- `min_score` / `max_score`：分数硬边界（抓“等级对了但分数虚高”）；
- `note`：给人看的说明。

## 2. 日期占位符：`@-80d`

```json
"created_at": "@-80d", "pushed_at": "@-76d"
```

`bench/run.py` 的 `_resolve()`（第 20 行）在加载时把它们换成本次运行时刻的绝对时间。

**为什么这么做**：如果写死 `2026-08-16`，三个月后 `dump_repo` 就变成“建库一年”，
测的就不是封顶逻辑，而是“样本老化”。用相对日期，样本永不过期。

## 3. `bench/run.py` — 跑分器

```python
for name, payload, expect in load_all():
    audit = rubric.score(rubric.build_context(payload))
    result = check(audit, expect)     # PASS / FAIL
打印表格 + 汇总，有 FAIL 就退出码 1
```

`--json` 给机器读（`tests/test_bench.py` 用它），`--verbose` 会打印失败样本的红旗。

## 4. 怎么加一个样本

1. 在 `bench/golden/` 新建 `xxx.json`，结构照抄现有的；
2. 用 `@-Nd` 写日期；
3. 想清楚 **`_expect` 是什么、为什么**——这一栏就是你的判断，别抄别人的；
4. `python bench/run.py`，如果 FAIL：
   - 先怀疑样本做得不像真实情况（最常见）；
   - 再怀疑规则（这时才动 `rubric.py`）。

> 加样本比调权重更有价值：一个 FAIL 的样本，等于一条“工具目前还判不准”的已知缺陷。

# 二、`tests/` — 44 个单测

## 分层

| 文件 | 测什么 | 特点 |
|---|---|---|
| `test_claims.py` | 宣称抽取 | 纯函数，无 fixture，最快 |
| `test_sources.py` | URL 解析、信号判定、平台识别 | **不联网**，只测解析逻辑 |
| `test_rubric.py` | 打分、封顶、拒答、确定性 | 用 `solid_facts()` / `hype_facts()` 现造数据 |
| `test_report.py` | 三种渲染 + CLI 退出码 | 部分用 `claimaudit/fixtures/` 里的快照 |
| `test_bench.py` | 黄金集回归 | 以子进程跑 `bench/run.py` |

## 几个值得看的测试

**`test_deterministic`（test_rubric.py）**
同一个 ctx、同一个 `now`，跑两次分数必须完全相等（保留 4 位）。
——这是“可复现”承诺的自动化版本。

**`test_dump_repo_is_capped` / `test_web_never_gets_s_grade`**
不只测分数，测**封顶是否真的生效**。这类测试保护的是“结构性判断”，比精度更重要。

**`test_html_escapes_user_content`（test_report.py）**
往 description 塞 `<script>alert(1)</script>`，断言渲染结果里没有它。

**`test_bench.py` 用 `subprocess` 而不是直接 import**
因为 `bench/run.py` 是个脚本（`sys.exit`），直接用子进程能同时验证“命令行入口是活的”。

## 为什么测试里要现造 facts

```python
def solid_facts(**over): ...
def hype_facts(**over): ...
```

不用固定 JSON 文件，而是用函数 + `**over` 覆盖字段。
好处：想测“把 commits 改成 3 会怎样”，直接 `solid_facts(commits=3)`，
不用维护一堆变体文件。

# 三、跑它们

```bash
python -m unittest discover -s tests -t .   # 44 个，约 0.1 秒
python bench/run.py                          # 7 个样本，表格式输出
```

CI（`.github/workflows/ci.yml`）在 Python 3.9 / 3.11 / 3.13 上跑同一套，
外加两条 CLI smoke 和一条“门禁必须失败”的断言。

---

## 四、这套体系解决了什么

| 没有基准时 | 有基准后 |
|---|---|
| “我感觉更准了” | 7 行 PASS/FAIL |
| 改了 A 坏掉 B，几天后才发现 | 改完立刻红 |
| 新需求 = 调阈值 | 新需求 = 加样本 + 加检查 |
| 无法解释分数为什么变 | `--json` 里逐条 evidence |

一句话：**基准不是为了证明工具好，是为了证明我这次的改动没让它变坏。**

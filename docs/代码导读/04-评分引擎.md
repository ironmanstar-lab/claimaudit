# 04 · 评分引擎：rubric.py（674 行）

整个项目的心脏。输入 `ctx`，输出一个 `Audit`（分数、等级、红旗、缺口、清单）。
**它不联网**——所有事实都来自 `facts`，所以同一份 facts 永远得同一分。

---

## 一、常量（第 22–61 行）

### `DIMENSIONS` · 第 22 行

```python
[("可验证性",25), ("证据密度",20), ("宣称一致",20),
 ("维护可信",15), ("风险敞口",10), ("上手成本",10)]
```

六维、加起来 100。为什么这么配：

- **可验证性最高（25）**：一个东西值不值得看，先看它说的话有没有口径；
- **宣称一致 20**：说的是不是真做了，这是“打假”最硬的部分；
- **风险敞口只有 10**：风险是“一票否决”型的（走封顶），不需要靠权重堆。

### `GRADES` · 第 31 行

`(阈值, 字母, 人话)`：85→S、70→A、55→B、40→C、其余 D。
**人话是给读者看的**，不是“合格/不合格”这种废话。

### `CONTENT_VERDICTS` · 第 39 行

文章/视频用另一套措辞：S“罕见：关键说法都能追到外部材料”、C“当线索用”。
一套话术套所有对象，读起来会失真。

### 关键词表

- `METHOD_WORDS`（第 47 行）：样本/回测/基准/口径/夏普/回撤/ICIR/消融/复现……
  → 出现越多，说明作者越愿意被检验；
- `DATA_COST_WORDS`（第 52 行）：tushare/付费/积分/API Key/订阅……
  → 隐性成本线索；
- `DISCLAIMER_WORDS`（第 57 行）：不构成投资建议/免责/风险自担……

### `MODULE_TOKEN` · 第 59 行

```python
`([A-Za-z_][\w./-]{2,40})`     # 反引号里的标识符
\b([a-z_]{3,20})/(?=\s|\||\Z)  # 形如 data/ 的目录式
```

用来抓“README 点名的模块”，再去和文件树比对。
**只看路径式**，因为散装标识符（环境变量名、函数名）不是模块（详见 `_module_claims`）。

## 二、两个数据结构

### `Outcome` · 第 65 行

一条检查的结果：`check_id / dim / title / weight / pct / evidence / redflag / action`。

### `Audit` · 第 77 行

整份审计结果。除分数等级外，还带 `dims`（六维明细）、`redflags`、`gaps`（证据缺口）、
`checklist`（自检清单）、`claims`（原始宣称）、`cap_reason`（封顶原因）、
`insufficient` + `insufficient_reason`（拒答）。

`as_dict()`（第 95 行）是 `--json` 的 schema：给 agent 用，字段稳定。

## 三、18 项检查逐个看

每条都是 `def _xxx(ctx, now) -> (pct, evidence, redflag, action) | None`。
**返回 `None` = 这条不适用**（比如网页没有文件树，`tests` 直接跳过）。

### 可验证性（25 分）

| 检查 | 权重 | 怎么算 | 为什么 |
|---|---:|---|---|
| `_claim_numbers` 第 155 行 | 10 | 可核口径的宣称占比（≥40% 满分） | 全是“更强更快”= 不可证伪 |
| `_external_refs` 第 169 行 | 8 | 外部链接 ≥3 → 1.0；1–2 → 0.6；0 → 0.2 | 有出处是最低成本的诚意 |
| `_method_disclosure` 第 184 行 | 7 | 方法论词 ≥4 → 1.0；2–3 → 0.7；1 → 0.4；0 → 0.1 | 只有结论没有方法，等于没说 |

`_external_refs` 的一个细节：排除**指向自己的链接**（`self_url` 前缀），
但**不排除 github.com**——那也可能正是它引用的第三方项目。这条曾经写错过。

### 证据密度（20 分）

| 检查 | 权重 | 怎么算 |
|---|---:|---|
| `_tests` 第 195 行 | 7 | 有测试→1.0；有代码无测试→0.1；无代码→0.2 |
| `_ci` 第 207 行 | 5 | 有 CI→1.0，否则 0.1 |
| `_repro` 第 215 行 | 4 | 演示数据+依赖清单→1.0；只有一样→0.6；都没有→0.15 |
| `_docs` 第 227 行 | 4 | ≥3 篇→1.0；1–2 篇→0.6；只有 README：≥3000 字→0.4，否则 0.15 |

设计意图：**证据是分层的**——跑起来（测试）> 一直能跑（CI）> 别人能跑（demo+依赖）> 说明白（文档）。

### 宣称一致（20 分）

| 检查 | 权重 | 怎么算 |
|---|---:|---|
| `_module_claims` 第 242 行 | 10 | README 点名的模块在文件树里的命中率 |
| `_license_claim` 第 285 行 | 5 | 说开源：LICENSE 可识别→1.0；NOASSERTION 或有文件→0.8；没有→0 + 红旗 + 封顶 C |
| `_install_claim` 第 300 行 | 5 | 说一键：依赖文件 ≤3→1.0；≤8→0.6；>8→0.15 + 红旗 |

`_module_claims` 的三个坑（都踩过）：

1. 反引号里的 `CLAIMAUDIT_TOKEN` 被当成模块名 → 只认含 `/` 的路径式；
2. `DSHQuant-v1.0.9-Release.zip` 这种文件名被当成模块 → 正则只允许 `[A-Za-z_][\w-]`；
3. 用“文件名包含”匹配太松（`src` 能在任何路径里撞上）→ 改为**顶层目录精确匹配**。

`_license_claim` 对 `NOASSERTION` 的处理很关键：GitHub 认出有 LICENSE 文件但类型不标准时
返回 NOASSERTION，不能当成“没有 LICENSE”，也不能当成“MIT”。

### 维护可信（15 分）

| 检查 | 权重 | 怎么算 |
|---|---:|---|
| `_recent_push` 第 316 行 | 7 | ≤30 天 1.0；≤60 0.8；≤120 0.55；≤180 0.35；≤365 0.2；更久 0.05（>365 加红旗） |
| `_cadence` 第 336 行 | 4 | 提交/月 ≥4 1.0；≥1 0.6；>0 0.3；0 0.1 |
| `_bus_factor` 第 352 行 | 4 | 贡献者 ≥5 1.0；3–4 0.8；2 0.6；1 → 0.25（star ≥1000 时加红旗） |

`_recent_push` 用 `days_since(pushed_at, now)` **动态算**，不读死字段——
这样测试可以注入固定 `now`，样本也不会随时间老化。

### 风险敞口（10 分）

| 检查 | 权重 | 怎么算 |
|---|---:|---|
| `_promo` 第 372 行 | 4 | 无钩子 1.0；1 个 0.5；≥2 个 0 + 红旗 |
| `_binaries` 第 392 行 | 3 | 有二进制/node_modules → 0 + 红旗 + 封顶 C |
| `_disclosure` 第 412 行 | 3 | 有免责 1.0；无免责但有收益宣称 → 0 + 红旗 + 封顶 C；其余 0.4 |

`_promo` 的关键细节：**逐行判断**，跳过含元信息标记的行。
否则“检测（加群/网盘/私域）→ 0 分”这句规则说明会把项目自己判成引流页。

### 上手成本（10 分）

| 检查 | 权重 | 怎么算 |
|---|---:|---|
| `_deps_cost` 第 423 行 | 5 | 依赖 ≤2 1.0；≤6 0.7；>6 0.35；需自备付费数据 → 上限 0.45 |
| `_quickstart` 第 442 行 | 5 | 安装+用法都有 1.0；一处 0.6；没有 0.2 |

## 五、加分项：红旗、缺口、封顶、拒答

### `_extra_redflags()` · 第 477 行 — 全局红旗

不看单条检查，只看整体：

- 有收益宣称 → “必须配实盘净值 + 样本外验证”；
- 绝对化 ≥3 处；
- **star ≥3000 且建库 <60 天** → “注意投放/刷星”；
- 仓库 archived；
- issue >200 但贡献者 ≤1；
- 文档 <300 字却在吹数量。

### `_gaps()` · 第 502 行 — 证据缺口

专门列“我们没有核到的东西”：视频无字幕、没拿到文件树、没有 LICENSE、
以及**几乎永远成立的一条**：“没有实盘/生产使用记录”。

这一节比分数更重要：分数是判断，缺口是边界。

### `_ceiling()` · 第 523 行 — 三条封顶

```python
if commits <= 5 and age > 30天     → 最高 B（一次性发布）
if 二进制 or node_modules          → 最高 C（不可审计）
if 说开源但没 LICENSE              → 最高 C
if 有收益宣称但没免责              → 最高 C
if 单人维护且 >180 天没更新        → 最高 C
```

**为什么要封顶**：加权求和有个致命弱点——**漂亮的文档可以投票盖过空心的事实**。
一个 3 次提交的仓库，只要 README 写得够细、测试目录够多，照样能算出 75 分。
封顶让“结构性事实”有一票否决权。

注意它返回的是 `(字母, 原因)`，取**最严的那个**，并把原因写进红旗第一条。

### `_insufficient()` · 第 558 行 — 拒答

```python
if transcript_required              → True（视频无字幕）
if 内容类 且 正文<200 且 宣称<3     → True（又短又没料）
```

命中时 `grade = "—"`，`verdict` 换成“证据不足，暂不定级”。

**这是整个工具的道德底线**：宁可说“我核不了”，也不给一个看起来专业的假分数。
0.1.0 版本只用“<200 字”判断，结果 180 字的诈骗页反而被拒答——0.2.0 加了“宣称数 <3”这个并列条件。

## 六、`score()` · 第 569 行 — 打分主流程

```python
1. for 每条检查: 结果不是 None 就收进 outcomes
2. possible = Σ weight，earned = Σ weight × pct
3. total = earned / possible × 100        # ← 注意分母是“适用的权重和”
4. 按维度汇总 dims
5. total 映射到 GRADES → grade / verdict
6. _ceiling 封顶
7. _insufficient 拒答（覆盖 grade）
8. 红旗 = 检查级 redflag + 全局 + 封顶原因（去重）
9. 清单 = 未达 0.75 的检查的 action，按“还差多少分”排序，取前 8
```

### 最关键的一行：分母重新归一

```python
possible = sum(o.weight for o in outcomes)   # 只算可评估的
```

如果网页不适用 `tests/ci/repro/docs`（共 20 分），分母就是 80 而不是 100。
**不这么做的后果**：一篇文章永远拿不到 60 分以上，看起来像“文章都不可信”，是规则的错，不是文章的错。

### 清单怎么排序

```python
sorted(outcomes, key=lambda x: x.weight * (1 - x.pct), reverse=True)
```

按“丢了多分”排序——先补最值钱的那条，而不是按检查表顺序。

## 七、`build_context()` · 第 655 行

把 payload 摊平成 rubric 吃的 ctx：

```python
{source, target, facts, text, claims}
```

`text` 的取法有优先级：`readme.text` → `facts.text` → `facts.transcript`。
这个顺序是刻意的：README 永远比网页全文更接近“作者想让你看到的话”。

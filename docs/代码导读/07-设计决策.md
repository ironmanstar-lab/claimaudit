# 07 · 设计决策：为什么是现在这个样子

前面六篇讲“代码怎么跑”，这一篇讲“为什么这么写、哪些路走过又退了”。

---

## 决策 1：审核“宣称”，不审核“真假”

**被否掉的做法**：让模型读完仓库，直接输出“这个项目可靠/不可靠”。

为什么不行：

- **不可复现**——同一句话问两次可能两个答案，报告就没有公信力；
- **不可反驳**——读者不同意，只能“我觉得不服”；
- **责任错位**——判断真假需要领域知识，工具没有这个资格。

**现在的做法**：只回答“它说的这些，有没有可核的证据；
核不到的部分是什么”。结论分等级，但每条都能追到一句事实。

> 一句话总结：**工具负责举证，你负责判断。**

---

## 决策 2：规则引擎，而不是 LLM

| | LLM 打分 | 规则打分 |
|---|---|---|
| 一致性 | 每次可能不同 | 完全一致 |
| 成本 | 需要 Key/钱 | 0 |
| 离线 | 不能 | 能 |
| 可解释 | “模型觉得” | 命中的是 `_recent_push` 的 76 天 |
| 可改 | 改 prompt，效果玄学 | 改一行阈值 |

**LLM 不是在项目里消失了，而是被放到了正确的位置**：
`SKILL.md` 规定 agent 先跑 CLI 拿事实，再用模型做解释与对话。
顺序反了，就是“先下结论再找理由”。

---

## 决策 3：零依赖（纯 stdlib）

- `pip install` 在受限网络里经常失败，而这个工具的第一步就是“在不信任的环境里跑”；
- 依赖越少，审计一个“声称零依赖”的项目时，自己越站得住；
- 代价：没有 `requests` 的重试/连接池，全部手写（`http.py` 200 行）。

零依赖不是信仰，是**为了让第一次运行的门槛降到最低**。

---

## 决策 4：加权求和 + 三条封顶

加权求和天生可以被“堆料”欺骗：README 写得漂亮、测试目录塞几个空文件，
分数就能上去。所以必须有**不参与加权的一票否决**：

| 封顶 | 挡的是什么 |
|---|---|
| commits ≤5 且建库 >30 天 → B | 文档精美的一次性发布 |
| 含二进制/node_modules → C | 无法审计的交付 |
| 说开源没 LICENSE → C | 法律上不可用的“开源” |
| 收益宣称无免责 → C | 卖课/荐股类内容 |
| 单人维护且 >180 天没更新 → C | bus factor = 1 的停更项目 |

**封顶原因必须写进红旗第一条**，否则用户会觉得“分数被莫名其妙压了”。

---

## 决策 5：证据不足就拒答

0.1.0 只判断“正文 <200 字 → 拒答”。上线后立刻发现：

> 180 字的卖课文案，因为“太短”被拒答；越像骗子，越拿不到分。

0.2.0 改成 **“又短又没料”才拒答**（<200 字 **且** 可判定宣称 <3 条）。

保留下来的拒答条件：

- 视频没有字幕（口播是主要载体，缺了就什么都核不了）；
- 内容既短又无宣称（确实没什么可判的）。

---

## 决策 6：分母要按“适用性”重新归一

```python
possible = sum(o.weight for o in outcomes if 适用)   # 不是固定 100
```

如果不这么做：一篇文章永远缺 20 分的“证据密度”，
哪怕它写得再好也上不了 60，读者会以为“文章都不可信”——那是规则的锅。

**`None` 表示“不适用”，0 表示“适用但做得很差”**，这两件事必须分开。

---

## 决策 7：报告里必须有「证据缺口」一节

分数是判断，缺口是边界。用户真正要决策的是：

> “它没被核实的部分，我能不能接受？”

所以 `_gaps()` 永远会列出：
视频无字幕、未拿到文件树、无 LICENSE、**没有实盘/生产使用记录**（几乎永远成立）。

把边界写在明面上，比把分数调准更重要。

## 踩坑清单（真实发生过的）

| # | 坑 | 现象 | 修法 |
|---|---|---|---|
| 1 | 表格碎片被当宣称 | 报告里出现 `…\| factors/ \| 因子引` | `_line_around` 取整行 + 清洗 Markdown |
| 2 | 导航标题被当宣称 | 别人的文章标题进了「它说」列 | 丢 `<a>` 文本 + `_looks_like_headline` |
| 3 | 规则说明被当宣称 | “宣称开源却没有 LICENSE → 最高 C”被当成收益承诺 | `_is_meta_line` + 收窄 `收益率?`→`收益率` |
| 4 | 环境变量被当模块名 | `CLAIMAUDIT_TOKEN` 去和文件树比对 | 只认路径式 + 顶层目录精确匹配 |
| 5 | `cto` 命中 `factor` | 英文词表没有词边界 | `\bcto\b` |
| 6 | 描述引流反而被判引流 | 列举“加群/网盘/私域”的表格 | `_promo` 逐行过滤元信息 |
| 7 | 短卖课文案被拒答 | 见决策 5 | 拒答条件加“宣称数” |
| 8 | 自审拿 A 带 3 条假红旗 | 用自己审自己，一眼看出误报 | 1–6 修完 → S 86.7 零红旗 |

> 第 8 条最重要：**拿工具审自己**，是发现误报最快的办法。

## 明确不做的事（非目标）

| 不做 | 原因 |
|---|---|
| 判断代码质量/安全漏洞 | 那是 code audit，不是 claim audit |
| 预测项目会不会成功 | 没人能做，做了就是骗子 |
| 自动下单/执行 | 越界，且责任无法界定 |
| 突破登录墙/反爬 | 拿不到就写“未获取”，不猜 |
| 给唯一真相分 | 分数是讨论工具，不是判决书 |

## 扩展指南

### 加一条检查

```python
# 1) 写函数
def _has_changelog(ctx, now):
    paths = (ctx["facts"].get("tree") or {}).get("paths") or []
    if not paths:
        return None                      # 不适用 → 跳过
    ok = any(p.lower().startswith("changelog") for p in paths)
    return (1.0 if ok else 0.2,
            "有 CHANGELOG" if ok else "没有 CHANGELOG",
            None,
            "让作者补一个变更记录" if not ok else None)

# 2) 注册（注意权重会让总分归一，先跑 bench）
("has_changelog", "证据密度", 3.0, _has_changelog),
```

### 加一个数据源

1. 新建 `sources/xxx.py`，实现 `probe()`，返回同样的 payload 结构；
2. `cli.load_payload()` 里加一个分支；
3. `rubric` 里需要的检查加 `None` 判断（没有对应字段就跳过）。

### 加一种输出

模仿 `render_html()` 写一个纯函数，在 `cli` 里加分支。
**不要**改 `Audit` 的结构——三种输出共享它。

## 版本策略

- **0.x**：schema 与 rubric 都可能变；`--json` 字段尽量只加不改；
- 每次改规则，`bench/` 必须全绿，否则不算通过；
- `CHANGELOG.md` 记录「改了什么 + 为什么」，不只是「改了什么」。

---

## 最后

这套代码只有 ~2300 行，但它遵守三条纪律：

1. **事实与判断分离**（sources vs rubric）；
2. **判断可复现**（规则 + 固定 now + 快照）；
3. **不确定就说不确定**（拒答 + 缺口）。

如果哪天要把它改到面目全非，希望这三条还在。

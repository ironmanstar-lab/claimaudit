# 评分细则（rubric v0.1）

18 条检查，六维加权，外加三条封顶与一条拒答。所有阈值都在
`claimaudit/rubric.py` 里，改一行就能改性格。

## 一条检查怎么算分

每条检查输出三样东西：

| 字段 | 含义 |
|---|---|
| `pct` | 0–1，这一检查满足到什么程度 |
| `evidence` | 一句话，**必须指向具体事实**（文件数、日期、条数） |
| `redflag` | 可选；命中就进红旗区，并可能触发封顶 |

总分 = `Σ(weight × pct) / Σ(weight)` × 100，**只对可评估的检查求和**。
不适用的检查直接剔除并重新归一，不会用 0 分把总分拖死。
（例：文章没有文件树，`tests/ci/repro/docs` 四条整条不参与。）

## 六维与 18 条检查

### 可验证性（25）

| id | 权重 | 满分条件 | 掉分点 |
|---|---:|---|---|
| `claim_numbers` | 10 | 提取到的宣称里 ≥40% 带数字口径 | 全是「更好/更强/更快」这类不可证伪表述 |
| `external_refs` | 8 | 正文 ≥3 个指向自己的外部链接 | 0 个 → 0.2；1–2 个 → 0.6 |
| `method_disclosure` | 7 | 出现 ≥4 处方法论词（样本/回测/基准/口径/夏普/回撤/复现…） | 0 处 → 0.1 |

### 证据密度（20）

| id | 权重 | 满分条件 | 掉分点 |
|---|---:|---|---|
| `tests` | 7 | 有测试文件 | 有代码但 0 测试 → 0.1 |
| `ci` | 5 | 有 CI 配置 | 无 → 0.1 |
| `repro` | 4 | 演示数据 + 依赖清单都在 | 都没有 → 0.15 |
| `docs` | 4 | ≥3 篇文档 | 只有 README 且 <3000 字 → 0.15 |

### 宣称一致（20）

| id | 权重 | 满分条件 | 掉分点 |
|---|---:|---|---|
| `module_claims` | 10 | 正文点名的模块名，≥50% 能在文件树找到 | 找不到 = 宣称与实现脱节 |
| `license_claim` | 5 | 说开源 + LICENSE 可识别 | 说开源却无 LICENSE → 0，且封顶 C |
| `install_claim` | 5 | 说一键 + 依赖文件 ≤3 | 说一键但依赖 >8 → 0.15 |

> `module_claims` 只认形如 `factors`/`risk_layer` 的标识符；文件名、版本号、
> 中文标识会被丢掉 —— 否则「DSHQuant-v1.0.9-Release.zip」会被当成模块。

### 维护可信（15）

| id | 权重 | 满分条件 | 掉分点 |
|---|---:|---|---|
| `recent_push` | 7 | ≤30 天有提交 | 120 天 → 0.55；>365 天 → 0.05 |
| `cadence` | 4 | ≥4 次提交/月 | <1 次/月 → 0.3 |
| `bus_factor` | 4 | ≥5 位贡献者 | 单人 → 0.25 |

### 风险敞口（10）

| id | 权重 | 满分条件 | 掉分点 |
|---|---:|---|---|
| `promo` | 4 | 无引流钩子 | ≥2 个（加群/网盘/私域/名额）→ 0，且进红旗 |
| `binaries` | 3 | 不提交二进制与 `node_modules` | 命中 → 0，并封顶 C |
| `disclosure` | 3 | 有免责/风险声明 | 有收益宣称却没声明 → 0，并封顶 C |

### 上手成本（10）

| id | 权重 | 满分条件 | 掉分点 |
|---|---:|---|---|
| `deps_cost` | 5 | 依赖文件 ≤2 且无需自备付费数据 | 依赖 >6 → 0.35；需买数据/Key → 上限 0.45 |
| `quickstart` | 5 | 有安装 + 用法 | 一条都没有 → 0.2 |

## 等级

| 分数 | 等级 | 含义 |
|---:|---|---|
| ≥85 | S | 可以当依赖用 |
| ≥70 | A | 值得投入时间，按缺口补齐再信任 |
| ≥55 | B | 有真东西但掺水，先自检 |
| ≥40 | C | 宣传远大于交付，只当素材 |
| <40 | D | 证据链不成立 |

内容类目标（文章/视频/文案）用另一套结论措辞，并**最高只给 A**：
没有代码可审计，就不该拿 S。

## 三条封顶

加权求和最大的问题是「漂亮的文档可以投票盖过空心的事实」。所以：

1. `commits ≤ 5` 且建库 > 30 天 → **最高 B**（一次性发布，不是活的代码库）
2. 交付含二进制或 `node_modules` → **最高 C**（无法审计）
3. 宣称开源无 LICENSE、或收益宣称无免责 → **最高 C**

命中时红旗第一条会写「评分封顶：…」，原始分仍然显示 —— 你可以看到它本来能得多少。

## 拒答

以下情况输出 `grade = "—"`，只列缺口，不给等级：

- 视频没有字幕/文案（口播里的承诺一条都没法核）
- 内容类目标正文不足 200 字
- 抓取失败（报告会写明哪一步失败）

这条规则是整个工具的道德底线：**宁可拒答，也不给一个看起来专业的假分数。**

## 调整建议

- 你更在意维护活跃度：把 `recent_push` 提到 10、`cadence` 提到 6。
- 你主要看「能不能直接依赖」：把 `tests` 提到 12、`binaries` 提到 6。
- 你觉得封顶太狠：删掉 `_ceiling()` 里对应那一行——但先想想它挡的是什么。
